# Background Unity UI Input Bridge Design

## Goal

Allow the existing `window_message_probe` client binary to request one left click at a client-relative coordinate in Revolution Idle without focusing or foregrounding the game window. The installed BepInEx IL2CPP plugin will receive the request and invoke the Unity uGUI handler on Unity's main thread.

The initial live test uses client coordinate `(1200, 80)`.

## Scope

The MVP supports one command: a left click at a client-relative point. It preserves the probe's optional `--focus` behavior, but the default path must not call `SetForegroundWindow` or otherwise activate the game.

The MVP targets Unity uGUI. It dispatches pointer handlers directly and does not attempt to mutate legacy `Input.GetMouseButtonDown()` state, emulate raw HID input, support dragging, or provide authenticated IPC.

## Architecture

The client locates the single visible `Revolution Idle.exe` window using its existing process-image matching. It posts one private Win32 message to that window.

The plugin installs a Win32 window subclass from its Unity `MonoBehaviour.Update()` method after the game window exists. The subclass callback validates and enqueues matching commands only. It must not call Unity APIs, block, or log.

The same Unity component drains the bounded command queue during `Update()`. It validates the coordinate against the current client area, converts from Windows top-left client coordinates to Unity bottom-left screen coordinates, raycasts through the current `EventSystem`, and dispatches pointer-down, pointer-up, and pointer-click handlers to the top valid uGUI target.

```text
window_message_probe
    -> PostMessageW(private WM_APP message)
    -> Unity HWND subclass callback
    -> bounded click queue
    -> ScoreTicker.Update()
    -> EventSystem.RaycastAll
    -> ExecuteEvents pointer down/up/click
```

## Message Protocol

- Message ID: `WM_APP + 0x417`.
- `wParam`: nonzero per-process request ID generated by the sender.
- `lParam`: x in the low 32 bits and y in the high 32 bits.
- Coordinates are unsigned client-area pixels measured from the top-left corner.
- The sender uses `PostMessageW` once per click request. It no longer sends `WM_MOUSEMOVE`, `WM_LBUTTONDOWN`, or `WM_LBUTTONUP` for the bridge path.
- No pointers or process-owned memory cross the message boundary.

The plugin rejects zero request IDs, out-of-range coordinates, and duplicate IDs. Its queue is bounded at 32 pending clicks; a full queue drops the new request. Delivery remains best-effort because this MVP has no acknowledgement channel.

## Window Hook Lifecycle

The plugin uses `SetWindowSubclass`, `DefSubclassProc`, and `RemoveWindowSubclass` with a fixed subclass ID and a callback delegate rooted for the complete hook lifetime.

Before installation, the plugin verifies that the selected window belongs to the current process and that its owner thread is the thread currently running `Update()`. If either check fails, it does not install the hook.

All unrelated messages are forwarded through `DefSubclassProc`. The bridge message is consumed after validation. `WM_NCDESTROY`, component destruction, and application shutdown stop acceptance, remove the subclass on the owner thread, clear queued commands, and only then release bridge state. If Unity recreates the window, the component detects the stale handle and attaches to the replacement.

## Unity Dispatch Semantics

For each accepted click, the main-thread dispatcher:

1. Reads the current Win32 client rectangle and Unity `Screen` dimensions.
2. Rejects a point outside the client rectangle or unusable dimensions.
3. Scales the client coordinate into Unity screen pixels when the dimensions differ and flips the y-axis.
4. Creates left-button `PointerEventData` with click count one.
5. Calls `EventSystem.RaycastAll` and selects the first valid result.
6. Dispatches pointer-down, pointer-up, then pointer-click through `ExecuteEvents` for that hit hierarchy.

The plugin logs bridge installation and one concise result for each requested click, including whether a target was hit and its name. Exceptions are contained within the plugin and must not escape into the native window procedure or Unity update loop.

## Safety and Limits

- The default sender path never focuses the game. `--focus` remains an explicit opt-in.
- `WM_APP` is not authentication. Any local process permitted by Windows message-integrity rules could submit this fixed message. That is acceptable for this local MVP but not for a hostile multi-user environment.
- Direct uGUI dispatch triggers handlers such as `Button.onClick`; it does not make Unity's legacy input polling report a physical mouse transition.
- A non-uGUI target or custom code that exclusively polls Unity input state will not respond.
- The plugin does not move the system cursor.

## Verification

Automated checks cover protocol packing/decoding, duplicate and bounds rejection, coordinate conversion, queue limits, and sender argument behavior. Build verification uses the repository's pinned Rust 1.97.1 toolchain and the existing .NET plugin/test projects. `cargo fmt` is not run.

The live test is staged:

1. Build and install the updated plugin without altering game saves.
2. Restart the already-running game so BepInEx loads the new DLL.
3. Confirm the BepInEx log reports a successful bridge hook.
4. Record the foreground window, run one no-focus click at `(1200, 80)`, and immediately record it again.
5. Confirm the foreground window did not become the game and the plugin logged exactly one dispatch with the raycast target.
6. Report the observed game effect separately; lack of a visible effect is not treated as success merely because the message was received.

The game will not be force-terminated. If a restart cannot be performed safely, live validation pauses for the user to close and reopen it.
